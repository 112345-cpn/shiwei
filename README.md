# 拾味 SHIWEI v2

本地生活双边平台。消费者找店、看评价、买券；商家入驻、上券、回评、看经营数据；平台运营审核、对账。

对标：**大众点评的结构** + **小红书的发现入口**。

---

## 为什么重做

v1 是教学项目改造，10 张表、5180 行 Java，能跑但是个「单边目录」：用户能浏览、能写笔记、能抢券，但**没有商家这个角色**，订单生成即结束，商户评分是写死的假数据。

v2 修的是结构，不是加功能：

| 域 | v1 | v2 |
|---|---|---|
| 需求侧 | 浏览 / 笔记 / 关注 / 抢券 | 增加搜索、附近、榜单、推荐位 |
| 供给侧 | **无** | 商家入驻、员工与核销员、券管理、回评、经营看板 |
| 资金侧 | 下单即完成 | 支付 → 核销 → 退款 → 对账，四段都有状态 |
| 内容资产 | 笔记孤立，商户分数写死 | **评价必须挂已消费订单**，聚合出真实评分 |

## 目录结构

按领域分包，不是按 controller/service/mapper 分层。一个业务域的改动不出一个包。

```
com.shiwei
├── common          基础设施：响应包装、异常、拦截器、token、配置
│   ├── annotation  @PublicApi / @RequireRole
│   ├── config      MyBatisPlus / RabbitMQ / Jackson / OpenAPI
│   ├── context     UserContext（ThreadLocal）
│   ├── exception   ErrorCode（70+ 业务码）/ BizException / 全局处理
│   └── security    TokenStore（token 与 user→tokens 双向索引）
├── auth            登录注册、验证码、会话
├── user            用户资料、关注关系
├── merchant        商家主体、入驻审核、员工
├── shop            门店、分类、营业时段、评分聚合
├── review          评价、商家回复、有用投票、标签
├── content         探店笔记、评论、点赞
├── trade           券、订单、支付、核销、退款
├── settlement      日对账
├── discovery       搜索、附近、热搜、榜单
└── admin           平台运营后台接口
```

## 数据库

29 张表，7 个域，见 `sql/schema.sql`。几个刻意的设计：

**1. 金额全用 int 存分。** 不用 `decimal` 也不用 `double`，避免四舍五入和浮点误差。

**2. `tb_review.order_id` 有唯一索引。** 一单一评，从数据库层面堵住刷评。评价必须来自已核销订单，这是点评类产品真实性的根 —— 教学项目通常直接给个 `tb_review` 让你随便发。

**3. 评分冗余两份。** `tb_shop.rating` 给列表排序用（避免每页 join 聚合表），`tb_shop_rating` 存分项明细和星级分布给详情页用。两份都由 MQ 异步刷，定时任务兜底重算。

**4. `tb_verify_record.order_id` 唯一索引。** 核销幂等不靠代码里 `if (status == 1)` 判断，靠数据库唯一约束兜底。两次并发请求只有一条能插进去。

**5. 库存扣减是带条件的 UPDATE，不是「先查后改」。** `UPDATE ... SET stock = stock - n WHERE stock >= n`，并发时数据库行锁把请求串行化，影响行数为 0 就是没抢到。查完再改中间有窗口，两个请求能同时读到「还有 1 张」。

**6. 状态流转同样靠条件更新。** 支付是 `WHERE status = 0`，核销是 `WHERE status = 1`，退款审核是 `WHERE status = 0`。少写这个条件，双击提交就能重复退款、重复回滚库存。

**7. 对账表拆两层。** `tb_reconciliation` 是日批次（商家维度汇总），`tb_reconciliation_detail` 是逐单差异（平/我方多/渠道多/单边账）。有事能定位到具体哪一单。

**8. `tb_merchant_staff` 存核销权限。** 不是给 user 打个 `isVerifier` 标记，而是（商家, 用户, 门店）三元组。一个人可以在 A 店核销、在 B 店没权限。

## 已经做完

- [x] 数据库 schema（29 表）+ 桂林本地种子数据（8 门店、7 张券、12 条评价对应 12 笔已核销订单）
- [x] 统一响应 / 70+ 业务错误码 / 全局异常
- [x] token 会话：Redis Hash 存登录态，反向 `user→tokens` 索引支持角色变更后刷在线会话
- [x] 三级角色：消费者 / 商家 / 平台运营，注解式权限 `@RequireRole`
- [x] 登录注册：验证码登录（未注册自动建号）、密码登录、BCrypt
- [x] 商家入驻 + 平台审核（通过时自动升级角色、建 owner 员工记录、刷新 token）
- [x] 商家员工管理（运营 / 核销员，可限定门店）
- [x] 门店：二级分类树、列表（4 种排序）、详情、附近（经纬度矩形预筛 + 距离排序）
- [x] **评价**：提交（三道门校验）、图片、标签、列表（3 种排序）、汇总（分项 + 星级分布 + 高频标签）、商家回复、有用投票、平台审核
- [x] **评分聚合**：MQ 异步全量重算 + 每日凌晨校准兜底；`ON DUPLICATE KEY` 保证并发消费者不撞主键
- [x] **券**：商家建券（落草稿）、改券、上下架、门店在售列表；时间窗口四组关系校验（开售<停售、有效期<结束、有效期晚于停售、售价≤原价）
- [x] **下单**：条件更新扣库存防超卖、价格快照落单（不信任前端合计）、同券挂单数限制防占库存、核销码 6 位随机 + 唯一索引碰撞重试
- [x] **支付**：`WHERE status = 0` 挡住重复支付，`uk_order` 挡住重复流水；门店销量走 MQ 重算而不是 +1
- [x] **超时关单**：TTL 队列 + 死信做主路径，`OrderCloseJob` 每分钟扫表兜底；关单幂等，重复调用不会多回滚库存
- [x] **核销**：四道门（商家归属 → 门店授权 → 订单状态 → 券有效期）；重复扫码返回 `repeated=true` 而不是报错；`uk_order` 兜住幂等
- [x] **退款**：已核销不可退、券过期不可退、待审去重；审核通过一次性完成退款单/订单/流水/库存四步，全程同一事务
- [x] 容器化：`docker-compose up` 一键起 MySQL / Redis / RabbitMQ / App，schema 与种子数据自动导入

## 本地启动

### 方式一：Docker（推荐）

```bash
docker-compose up -d --build
# 首次构建 5-8 分钟
```

启动后：

| 服务 | 地址 |
|---|---|
| 应用 | http://localhost:8081 |
| 接口文档 | http://localhost:8081/doc.html |
| RabbitMQ 控制台 | http://localhost:15673 （guest/guest） |
| MySQL | localhost:3307 （root/123456） |
| Redis | localhost:6380 |

### 方式二：本地 IDE

需要本机已有 MySQL 8 / Redis / RabbitMQ，然后：

```bash
mysql -uroot -p < sql/schema.sql
mysql -uroot -p < sql/seed.sql
mvn spring-boot:run
```

连接信息用环境变量覆盖，见 `application.yml` 里的 `${MYSQL_HOST:localhost}` 写法。

## 已知限制

- 支付走的是 `MOCK` 渠道，不接真实渠道。`tb_payment.channel` 已经留了支付宝的枚举值。
- 附近查询用的是 SQL 算距离，10 万门店以上要换 Redis GEO 或空间索引。
- 图片上传目录默认 `./imgs`，容器里挂卷到 `/app/imgs`。
