# 设计问答

面试官问「你这个项目里最难的地方是什么」，其实是在挑一个点往下钻。
这份文档把每个关键设计拆成「他会怎么问 → 你怎么答 → 他可能接着追什么」，
答不上来的那一条就是还没消化的部分。

---

## 1. 库存怎么防超卖

**问**：1000 个人同时抢 100 张券，你怎么保证不超卖？

**答**：扣库存是一条带条件的 UPDATE：

```sql
UPDATE tb_voucher SET stock = stock - 1 WHERE id = ? AND stock >= 1
```

看影响行数，返回 0 就是没抢到。并发时 InnoDB 的行锁会把这条语句串行化，
`stock >= 1` 不成立的那次自然改不动。

**追问 1**：为什么不先 `select stock` 判断一下再 update？

查完到改之间有窗口。两个请求可以同时读到 `stock = 1`，然后都往下走，
一个扣成 0，一个扣成 -1。

**追问 2**：那用分布式锁不行吗？

行，但没必要。锁是应用层的互斥，条件更新是让数据库自己做互斥 ——
少一次 Redis 往返，也不会因为锁超时没释放把整条链路卡死。
**能用一条 SQL 解决的事不要引入分布式锁**，锁的成本在「怎么保证释放」上。

**追问 3**：那 Redis 预扣是干什么的？（见第 2 题）

## 2. 秒杀为什么不让接口直接落库

**问**：你秒杀接口为什么返回「排队中」？直接下单不行吗？

**答**：1500 QPS 打进来，数据库连接池先被打爆。后面的请求全卡在等连接，
响应时间从毫秒劣化到秒级 —— 这时候不是慢，是雪崩。

所以拆成三段：

| 段 | 做什么 | 为什么放这 |
|---|---|---|
| Redis + Lua | 判库存、判一人一单、扣减 | 内存操作，单机十万级 QPS |
| MQ | 排队 | 把突发流量削成平缓的消费速率 |
| DB | 真正落单 | 按消费者能力匀速写，不被打穿 |

接口只做第一段，成本是一次 Redis 往返。

**追问**：Redis 扣了库存，落库失败怎么办？

消费者失败时把 Redis 的库存加回去、把用户从「已购」集合里移除。
不回滚的话库存越抢越少，最后「显示有货但谁抢都失败」。

## 3. 一人一单怎么做的

**答**：Lua 脚本里 `SISMEMBER` 判断这个 userId 在不在 Set 里，
不在才 `SADD` 并 `DECR` 库存。判断和写入在 Redis 里原子完成。

**追问 1**：为什么不用数据库唯一索引？

也行，但那要求先把单插进去才知道重不重复。
秒杀场景下大部分请求应该在 Redis 就被挡掉，不该走到数据库。
唯一索引是**最后一道**，不是第一道。

**追问 2**：用户抢到不付款，15 分钟后单关闭了，他还能再抢吗？

能。关单时要把用户从 Set 里移除，否则他永远被判重复下单。
但注意关单是「改订单 + 回滚 DB 库存 + 释放 Redis 名额」三件事，
前两件在事务里，第三件必须等事务提交后再做 —— 见第 7 题。

## 4. 哪些地方做了幂等，分别靠什么

**问**：MQ 是至少投递一次，重复消息你怎么处理？

按场景选手段，不是一律加锁：

| 场景 | 手段 | 为什么选它 |
|---|---|---|
| 一单一评 | `tb_review.order_id` 唯一索引 | 重复插入直接抛 DuplicateKey，最省事 |
| 核销 | `tb_verify_record.order_id` 唯一索引 + 订单状态条件更新 | 状态更新挡住第二次，唯一索引兜住记录 |
| 退款审核 | `UPDATE tb_refund ... WHERE status = 0` | 商家双击提交时只有一次能改成功 |
| 评分聚合 | 全量重算 | 重算天然幂等，重复消费只是多算一次 |
| 秒杀落单 | 先查该用户这张券有没有未关闭的单 | Set 已挡住大部分，这是消息重投的兜底 |

**追问**：为什么评分用重算不用累加？

`sold = sold + 1` 遇到重复消息会算高，而且错了之后无法自愈。
`SUM(quantity)` 重算永远得到同一个结果 —— **能重算就别累加**。

## 5. 订单超时关闭怎么实现的

**答**：两层。

主路径是 RabbitMQ 的队列级 TTL：消息发到延迟队列，躺 15 分钟过期后
死信路由到消费队列。不用 delayed-message 插件，本地和服务器都不用额外装东西。

兜底是 `OrderCloseJob` 每分钟扫 `status = 0 AND expire_time < NOW()`。

**追问 1**：为什么还要兜底？

消息可能投递失败、消费者可能异常、RabbitMQ 可能重启丢消息。
只要有「靠消息驱动」的地方，就必须有一条「扫表」的退路。

**追问 2**：下单时 `expireTime` 怎么算的？

用 `RabbitMQConfig.ORDER_PAY_TTL_MS` 这个常量算，和队列 TTL 同源。
两边如果各写各的数字，改一处忘另一处，就会出现「消息先到但单没到期」或者反过来。

**追问 3**：重复消费会不会把已支付的单关掉？

不会。`markClosed` 的条件是 `WHERE status = 0`，付过款的单是 1，改不动。

## 6. 评价真实性怎么保证

**答**：`tb_review.order_id` 唯一索引，一单一评。提交时三道门：
订单属于你 → 订单已核销 → 这一单没评过。

**追问**：评分是怎么算出来的？

评价提交/审核通过后发 MQ，消费者全量重算该店的平均分、星级分布，
`ON DUPLICATE KEY UPDATE` 写进 `tb_shop_rating`，同时回写 `tb_shop.rating`
给列表排序用（避免每页 join 聚合表）。凌晨 3:30 有个定时任务全量校准一次。

**为什么要两份评分数据**：列表页只按分数排序，读 `tb_shop.rating` 就够；
详情页要分项和星级分布，读 `tb_shop_rating`。用空间换掉每页一次 join。

## 7. 为什么 Redis 操作要放在事务提交之后

**问**：你在关单里为什么要用 `afterCommit`？

**答**：关单是「更新订单 → 回滚 DB 库存 → 释放 Redis 名额」。
前两步在同一个事务里，第三步在 Redis。

如果 Redis 先放出去了、事务又回滚了：DB 里订单还是待支付、库存没回滚，
但 Redis 多了一张 —— 这张会被别人抢走，就是**真超卖**。

反过来，事务提交后 Redis 失败了，只是少卖一张（Redis 名额没释放），
可以用定时任务补。**少卖比超卖好**，这是取舍方向。

**追问**：那为什么下单时扣 Redis 反而在发消息之前？

因为秒杀的顺序是 Redis 先扣、MQ 再发。
如果先发消息再扣，消息到了消费者但库存没扣，消费者会按「有资格」处理。
先扣再发，最坏情况是扣了但消息没发出去 —— 这时当场回滚 Redis 就行。

## 8. 金额为什么用 int 存分

**答**：`0.1 + 0.2 != 0.3`，浮点数在二进制里表达不了十进制小数。
`decimal` 可以但读写要转换，还占更多空间。用 `int` 存分，
加减乘都是整数运算，没有误差，展示时除 100 就行。

**追问**：那分成、折扣怎么算？

用整数运算向下取整，比如折扣文案 `sale * 100 / original` 得到 `67`，
再格式化成 `6.7 折`。**不要在中间步骤引入浮点**。
