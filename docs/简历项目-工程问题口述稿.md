## 一、超时关单整套是死的（P0，最该讲的一条）

**现象**
下单后 30 秒不付款，订单应该自动关闭、库存回补。实测 500 单在 35 秒后**无一关闭**，
死信队列 `hmdp.seckill.order.dl` 的消息数永远是 0。

**根因**
两个错误叠在一起：

1. TTL（30 秒过期）设在了**下单消息自己身上**。但那条消息刚进队列就被消费者**立刻取走**了，
   它根本活不到过期那天 —— TTL 等于没设。
2. **延迟队列压根没声明**。死信队列一个生产者都没有，`closeOrder` 永远等不到消息。

> 关键认知：RabbitMQ 的"延迟"不是给消息定时，是**让消息在一个没人消费的队列里躺够时间，
> 过期后被转发到另一个队列**。所以 TTL 必须设在**队列**上，而且那个队列**必须没有消费者**。

**怎么改**
新增 `hmdp.seckill.order.delay` 队列：不配消费者 + 队列级 `x-message-ttl=30000` +
`x-dead-letter-exchange` 指回秒杀交换机、路由键 `seckill.order.dl`。
下单成功后在**事务提交之后**投递一条关单消息进去，30 秒后自动进死信队列被关单消费者处理。

**怎么讲**
> 「我一开始以为给消息设个 TTL 就能延迟，跑起来才发现关单从来没触发过。
> 查了队列监控发现死信队列消息数一直是 0。原因是下单消息一投进去就被消费者取走了，
> 等不到过期；而延迟队列我根本没声明。后来改成用队列级 TTL + 无消费者的延迟队列，
> 过期后自动进死信。还有一个细节：关单消息必须在事务提交之后投，不然事务回滚了还会关别人的单。」

## 二、WebSocket 推的订单号，进了浏览器就变样

**现象**
同一个订单，页面上两条通道显示两个不同的订单号：一条是 `...045853`，另一条是 `...045800`。
差在最后几位。

**根因**
订单号是雪花算法生成的 **19 位 long**。Java 的 long 最大能到九千多京，
但 **JavaScript 的数字只有 53 位精度**，超过 2^53 就开始抹零。19 位已经超了。

项目里本来有防护：`JacksonConfig` 全局把 `Long` 序列化成字符串。**但推送那条链路没走 Jackson** ——
`NotificationService` 用的是 Hutool 的 `JSONUtil`，它不认 Jackson 的配置，自己把 long 原样写成数字。

**怎么改**
推送时注入 `ObjectMapper`（就是 Spring 里那个配好的），用它序列化。两条通道从此一致。

**怎么讲**
> 「一个配置只对它管的那条链路生效。我全局配了 Long 转字符串，HTTP 接口没问题，
> 但 WebSocket 那条走的是另一个 JSON 库，根本不看这个配置。订单号 19 位，
> JS 只有 53 位精度，末尾几位直接被抹掉。后来推送改成用同一个 ObjectMapper 才对齐。」

## 三、WebSocket 通道建好了，业务从来没调用过

**现象**
`NotificationService` 写了完整的推送逻辑，但全项目**零调用**。也就是说这个功能是"零件齐了没装机"。

**根因**
建通道和接业务是两个人两件事，中间没人把它们接起来。

**怎么改**
在秒杀下单成功、事务提交之后，调 `pushSeckillResult(uid, orderId)` 推给对应用户。

**为什么必须"提交之后再推"**
先推后提交的话，万一事务回滚了，用户手机上已经弹出「抢到了」，数据库里却没有这个订单。
**顺序本身就是设计决策。**

**怎么讲**
> 「推送不是发出去就完事，得考虑时序。先推后提交，回滚的时候用户会收到一条假消息。
> 所以我把推送放在事务提交之后的回调里。」

## 四、三套限流，两套是空架子

**现象**
项目里写了三套限流：Sentinel 注解限流、按 IP 限流、Redis 固定窗口防刷。
实际只有锁库存那个接口真在用 Sentinel；`@IpRateLimiter` **一次都没被调用过**；
防刷拦截器遇到未登录用户**直接放行**（等于没防）。

**根因**
注解写了不等于生效。限流是"给某个方法加一道闸"，你不在方法上挂它，它就是一段死代码。

**怎么改**
- 秒杀下单：Sentinel 100 QPS
- 博客发布：20 QPS
- 登录：10 QPS + 按 IP 5 QPS
- 发验证码：**按 IP 1 秒 1 次**（不是按用户）

**为什么验证码要按 IP 限**
这个接口被调用的时候用户**还没登录**，没有用户身份可限。而且每发一条都是真金白银
（短信费 / 邮件配额），必须按来源 IP 卡。

**怎么讲**
> 「我原以为写了三套限流就三层防护，后来核对了一遍调用链，发现两套根本没挂到接口上。
> 另外验证码那个接口要按 IP 限而不是按用户 —— 因为那一刻用户还没登录。」

## 五、两套 MQ 队列名并存，配置文件里那套是死的

**现象**
`application.yaml` 里配了一套队列名，代码里硬编码了另一套。**实际生效的是代码里那套**，
yaml 里那套从头到尾没人用。

**根因**
配置和代码各写各的，没人对过。

**怎么改**
统一到一处，用 `rabbitmqctl list_queues` 实测确认：`order` 5 个消费者、`delay` 0 个、`dl` 5 个。

**怎么讲**
> 「判断配置生不生效，不能看文件，要看运行时。我是直接进容器跑 `rabbitmqctl list_queues`
> 看的消费者数量，跟设计对上了才算真的配对了。」

## 六、jar 打出来跑不了，报"没有主清单属性"

**现象**
`java -jar app.jar` 报 `no main manifest attribute`。

**根因**
pom 里缺 `spring-boot-maven-plugin`。普通 `maven-jar-plugin` 打的包不含启动类和依赖，
Spring Boot 需要这个插件做 **repackage** —— 把依赖塞进 jar，再在 `MANIFEST.MF` 里写上 `Main-Class`。

**怎么改**
pom 加插件，重新打包。

**怎么讲**
> 「这个坑很典型：代码没问题，打包方式不对。Spring Boot 的 jar 不是普通的 jar，
> 它要把依赖一起打进去并指定启动类，得靠 `spring-boot-maven-plugin`。」

## 七、nginx 没代理 `/ws`，WebSocket 握手被当普通请求

**现象**
本地直连后端握手正常，套上 nginx 之后连不上。

**根因**
WebSocket 握手是一个带 `Upgrade: websocket` 头的 HTTP 请求。nginx 默认按普通 HTTP 处理，
把这个头丢了，后端就当普通请求回了个 200，握手失败。

**怎么改**
`/ws` 的 location 里加：

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

**怎么讲**
> 「WebSocket 是靠 HTTP 协议升级建立的。nginx 默认不转发 Upgrade 头，
> 后端收到的就是一个普通请求，握手直接失败。这个用浏览器控制台看状态码最直观 —— 应该是 101，实际返回 200。」

## 八、压测时"成功了"其实没落库

**现象**
洪峰压测，HTTP 返回成功的数量和数据库里的订单数对不上。

**根因**
下单是异步的：Redis 预扣库存成功 → 立刻返回订单号 → **消息还在 MQ 里排队**。
HTTP 的成功只代表"进队列了"，不代表"落库了"。压测脚本一打完就查库，当然对不上。

**怎么改**
等队列消化完（轮询到订单数稳定）再校验，且校验规则改成「落库数 ≥ 成功响应数」而不是相等。

**怎么讲**
> 「异步链路的压测不能打完就查库。成功响应数代表进队列的数量，落库是后来的事。
> 我等队列消化完再比对，规则也从『相等』改成『不少于』—— 因为可能有重复消费被幂等挡掉。」

## 九、（已从简历撤下）消费端自调用，事务从来没生效

> 这条现在不在简历上，因为他说自己讲不清楚。但它是这个项目**技术上最值钱**的一个发现，
> 哪天想通了可以加回去。完整记录在 `FIXES.md` 第 1 节。

**现象**
秒杀下单流程看着正常：订单能建、库存能扣。但中间只要抛异常，已写入的数据**不回滚**，
还出现过"订单建了、库存没扣"的脏数据。

**根因**
```java
@RabbitListener(queues = "hmdp.seckill.order")
public void onMessage(SeckillOrderMessage msg) {
    asyncCreateVoucherOrder(msg);      // 同一个类里直接调自己
}

@Transactional
public void asyncCreateVoucherOrder(SeckillOrderMessage msg) { ... }
```

`@Transactional` 靠**动态代理**实现：Spring 给这个 Bean 生成了替身，只有**从外面**调用才会
经过替身、织入事务。类里面 `this.xxx()` 是直接找本人，**替身被绕过去了**，事务注解当场失效。

**怎么改**
三种解法：注入自身代理、用 `AopContext.currentProxy()`、或者把方法拆到另一个 Bean 里。

**一句话版本**
> 「同一个类里自己调自己，`@Transactional` 是不生效的，因为事务是靠代理织进去的，
> 自调用不经过代理。」

## 十、还没修的：按 IP 限流的规则会无限增长

`RateLimiterAspect.registerIpRuleIfNeeded` 每遇到一个新 IP，就往 Sentinel 的规则表里塞一条，
**永不回收**。IP 一多，规则列表会一直涨。

这是已知缺陷，能讲但别说已经解决了。标准说法：
> 「这块我目前是每来一个新 IP 注册一条规则，没做回收，量大了会一直涨。
> 正确的做法是用热点参数限流（`SphU.entry` 带参数），或者定期清理。」
